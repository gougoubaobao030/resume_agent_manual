# 1. 产品概述

## 1.1 产品定位

Resume Agent（RA）是一套面向招聘场景的 AI 辅助简历筛选系统。

系统围绕招聘人员的真实初筛流程，将自然语言 JD 转换为可调整的结构化评分要求，对 PDF 简历进行结构化解析，并针对候选人与岗位的匹配程度、候选人的潜力信号以及 HR 指定的人材特征提供可解释分析。

RA 的目标不是替代招聘人员做最终决定，而是：

- 将重复、机械的信息提取与初步比较交给系统；
- 帮助招聘人员快速区分候选人优先级；
- 用结构化理由与简历证据支持人工复核；
- 在传统岗位匹配之外，为非标准经历、成长能力与可迁移能力保留被发现的机会。

## 1.2 产品核心问题

传统简历初筛通常存在以下问题：

1. 简历数量大时，人工重复阅读学历、工作年限、技能、项目经历等信息，时间成本高；
2. 招聘人员快速浏览时容易遗漏项目成果、学习能力、跨岗位经验及可迁移能力；
3. 关键词筛选难以理解同义表达、上下文和实际职责之间的语义关系；
4. 只依赖岗位名称、学历或固定关键词，容易过早过滤经历路径不标准但能力相关的候选人；
5. 不同招聘人员的判断尺度可能不一致，缺少统一、透明且可复核的辅助依据；
6. AI 直接给分如果没有证据约束，容易产生“看起来合理但无法核实”的判断。

## 1.3 最终产品目标

RA 最终实现聚焦以下目标：

- 支持从自然语言 JD 自动生成结构化岗位要求；
- 允许 HR 对要求条目、权重和硬性条件进行人工修正；
- 支持单份和批量 PDF 简历上传；
- 支持“一名候选人对应多份 PDF”的文件夹式导入，并在上传前合并；
- 将简历解析为统一的 Candidate 数据；
- 根据岗位要求逐项进行语义匹配并生成综合匹配分；
- 对候选人进行固定维度的潜力信号分析；
- 支持 HR 自定义人材特征进行指定分析；
- 评分与能力判断尽量绑定简历事实，并提供证据校验状态；
- 保存候选人与评分结果，支持后续查看、重新评价与候选人池复用；
- 支持中文、日文、英文界面和分析结果；
- 在批量处理场景中保证单份失败不会导致整批失败。

# 2. 目标用户与典型场景

## 2.1 目标用户

- 企业招聘人员 / Recruiter；
- 企业 HR；
- 中小型招聘团队；
- 需要在短时间内处理大量候选人的项目负责人或用人部门。

## 2.2 典型使用场景

某岗位收到大量简历。HR 首先录入 JD，系统提取岗位要求；HR 根据实际招聘策略调整权重及硬性条件。随后批量上传候选人简历，系统完成解析和岗位匹配，并补充潜力信号、人材像及证据状态。

HR 不需要平均阅读所有简历，而是先根据匹配分、硬性条件、潜力信号和重点提示缩小范围，再进入候选人详情查看理由、证据、缺失信息及原始简历，完成最终人工复核。

## 2.3 核心使用原则

- **AI 辅助，不替代人工决策**；
- **先结构化，再评价**；
- **结果必须尽量可解释、可追溯**；
- **HR 可以覆盖模型给出的初始岗位结构**；
- **缺少证据时明确表示“证据不足”，而不是强行给出肯定结论**；
- **批量流程允许局部失败，避免单个异常拖垮整个任务**。

# 3. 最终业务流程

```text
用户登录
   ↓
创建 / 粘贴 JD
   ↓
LLM 解析岗位名称和 requirements
   ↓
HR 修改 requirement、权重、must-have
   ↓
保存 JD
   ↓
上传 PDF 简历
   ├─ 多份单体 PDF
   └─ 一个批次文件夹
        └─ 一级子文件夹 = 一名候选人
             └─ 多份 PDF 自动合并
   ↓
创建异步简历解析任务
   ↓
计算文件 SHA-256
   ├─ 已存在相同简历 → 复用 Candidate 并关联当前 Job
   └─ 不存在 → 提取 PDF 文本 → LLM 结构化
   ↓
保存 Candidate 与原始 PDF
   ↓
岗位匹配分析
   ↓
潜力信号分析（Auto）
   ↓
HR 指定人材特征分析（Specified，可选）
   ↓
候选人列表排序 / 批量再评价
   ↓
进入候选人详情
   ↓
查看理由、证据、缺失信息、证据状态及原始简历
   ↓
由 HR 做最终判断
```

# 5. JD 管理需求

## 5.1 JD 数据结构

一份 JD 最终由以下核心字段组成：

- `id`
- `job_title`
- `raw_text`
- `requirements[]`

每个 requirement 包含：

- `id`
- `name`
- `description`
- `category`
- `weight`
- `must_have`

分类范围：

- technical
- experience
- education
- other

## 5.2 权重规则

权重采用**相对权重**设计：

- 不要求人工凑成 100；
- HR 可以按照自己习惯的粒度设置，例如 10 / 20 / 30 或 11 / 12 / 15；
- 评分阶段由系统进行归一化；
- `weight = 0` 的要求不参与综合分计算；
- 权重反映不同岗位要求的重要程度。

该设计的目的，是避免 HR 为了满足“总和必须等于 100”的形式约束而增加额外操作。

## 5.3 must-have

`must_have` 用于标记需要单独关注的硬性条件。

must-have 不等同于“自动淘汰”。系统会独立汇总：

- 是否存在明确未满足；
- 是否存在证据不足、需要确认；
- 哪些 requirement 触发了失败或待确认。

最终是否淘汰仍由 HR 判断。

# 6. 简历上传与解析

## 6.1 支持格式

当前支持：

- 文本型 PDF 简历。

当前不保证：

- 图片扫描型 PDF 的 OCR；
- Word / Excel / 图片等其他简历格式。

## 6.2 两种上传方式

### A. 普通 PDF 上传

用于“一名候选人 = 一份 PDF”的常见场景。

用户一次可选择多份 PDF，系统按文件分别创建候选人解析任务。

### B. 候选人文件夹上传

用于履歴書、職務経歴書等“一名候选人存在多份 PDF”的场景。

约定：

```text
批次根目录/
├─ 候选人A/
│  ├─ 履歴書.pdf
│  └─ 職務経歴書.pdf
├─ 候选人B/
│  └─ resume.pdf
└─ 根目录文件.pdf   ← 忽略
```

规则：

- 一次只选择一个批次根目录；
- 根目录下的一级子文件夹代表一名候选人；
- 只处理候选人子文件夹根层的 PDF；
- 更深层目录中的 PDF 不纳入；
- 非 PDF 文件忽略；
- 同一候选人只有 1 份 PDF 时直接上传；
- 有 2 份及以上 PDF 时，前端先按稳定文件名顺序合并为一份 PDF，再上传后端；
- 合并后的文件名使用候选人子文件夹名。

## 6.3 解析流程

真实解析流程：

1. 读取 PDF；
2. PDF 文本提取属于同步阻塞操作，通过 `asyncio.to_thread()` 放入线程执行；
3. 文本为空时判定解析失败；
4. 将原始文本发送给 LLM；
5. 使用 Pydantic Schema 对模型输出进行结构校验；
6. 生成统一 Candidate；
7. 保存 Candidate、原始文本、结构化数据和原始 PDF。

## 6.4 Candidate 主要结构

候选人结构包含但不限于：

- 基本信息；
- 教育经历；
- 工作经历；
- 项目经历；
- 技能；
- 语言；
- 成果；
- 证书；
- Candidate Evidence；
- 原始简历文本；
- 提取元数据；
- 原始文件名。

解析原则：

> 简历解析阶段只提取已有事实，不主动补全未知事实，不根据岗位进行评价。

# 7. 批量任务与异常隔离

## 7.1 批量限制

- 每次最多上传 30 份 PDF；
- 批次中每份简历拥有独立状态；
- 单份失败不影响其他文件继续执行。

## 7.2 后台任务状态

任务级状态包括：

- pending
- running
- completed
- completed_with_errors
- failed

单项状态包括：

- pending
- running
- success
- failed

前端可轮询任务状态并逐步展示结果。

## 7.3 并发策略

简历解析使用异步任务和 `asyncio.gather()` 执行多个 worker，并通过 `Semaphore` 控制并发数量。

当前实现的简历解析并发上限为：

```text
3
```

设计目的：

- 避免同步 LLM 请求长期占用 Web worker；
- 提高多份简历场景的吞吐；
- 避免无限并发导致模型供应商限流或本机资源过载。

## 7.4 失败重试

失败的单个简历任务项可重新解析。

限制：

- 仅失败项可以重试；
- 任务仍在执行时不能重复触发；
- 重试前必须仍保留对应 pending PDF；
- 重试过程中同步切换状态，避免双击生成重复 Candidate。

# 8. Candidate 与 Job 的关系

## 8.1 Candidate 为全局实体

RA 将候选人与岗位关系拆分：

```text
Candidate
    ↑
    │
JobCandidate
    │
    ↓
Job
```

Candidate 表示“这个人 / 这份唯一简历实体”。

JobCandidate 表示“该 Candidate 被加入了哪个 Job”。

因此同一 Candidate 可以被多个岗位复用，不需要为每个岗位重复创建候选人副本。

## 8.2 精确哈希去重

上传 PDF 时计算 SHA-256。

若数据库中已经存在完全相同 `resume_hash` 的 Candidate：

- 不重新解析 PDF；
- 不再次调用简历结构化 LLM；
- 复用已有 Candidate；
- 仅创建 Candidate 与当前 Job 的关联；
- 如果该关联已经存在，则直接识别为 already-linked。

当前去重仅针对**文件字节完全一致**的情况。

不进行：

- 模糊文本去重；
- 姓名相似判断；
- “同一个人不同版本简历”的自动合并。

# 9. 岗位匹配分析

## 9.1 分析单位

岗位匹配并不是直接让模型给一个总分。

系统首先针对每一条 JD requirement 生成独立结果：

- requirement_id
- requirement_name
- must_have
- original_weight
- normalized_weight
- status
- score
- confidence
- reason
- evidence
- missing_information
- needs_raw_review

## 9.2 匹配状态

单条要求支持：

- `matched`
- `partially_matched`
- `not_matched`
- `insufficient_evidence`

## 9.3 置信度

- high
- medium
- low

置信度表示当前判断证据的充分程度，不等同于候选人好坏。

## 9.4 综合分

系统依据各 requirement 的分数和归一化权重计算综合 Job Match Score。

综合分范围：

```text
0 - 100
```

用途：

- 帮助 HR 排序；
- 缩小优先阅读范围；
- 快速区分明显高匹配和低匹配候选人。

综合分不作为自动录用 / 淘汰指令。

## 9.5 缺失信息

当简历没有提供足够信息时，系统应保留：

- missing_information
- insufficient_evidence
- low confidence
- needs_raw_review

而不是将“不知道”直接解释为“不具备”。

# 10. Evidence 校验

## 10.1 设计目标

LLM 生成“理由 + 引用证据”并不代表证据天然可信。

RA 在评分结果和人才能力分析之后增加 Evidence Verification，对模型给出的证据进行二次校验。

## 10.2 Evidence 状态

人才能力分析中采用三态：

- `verified`：证据存在且验证通过；
- `needs_review`：模型给出了证据，但定位或验证存在问题，需要人工复核；
- `insufficient_evidence`：模型没有提供足够证据支持该判断。

## 10.3 交互语义

界面不把“模型说有能力”直接等价为事实。

HR 可以区分：

- 已验证；
- 待复核；
- 证据不足。

该机制用于降低“模型结论看起来很合理，但简历里实际找不到依据”的风险。

# 11. 潜力信号分析（Auto）

## 11.1 产品定位

早期方案中的“证据潜力分 + 开放发现分”在最终产品中收敛为**结构化潜力信号分析**。

它不是另一个与岗位匹配并列的 0-100 分数，而是回答：

> 从候选人已经提供的经历中，能否发现值得 HR 进一步关注的成长与迁移信号？

## 11.2 七个固定维度

Auto 模式必须覆盖七个维度：

1. `learning_transfer`  
   学习与迁移能力

2. `analytical_problem_solving`  
   分析与问题解决

3. `initiative_drive`  
   主动性与推动力

4. `persistence_execution`  
   持续执行与落地

5. `adaptability_resilience`  
   适应性与韧性

6. `reflection_growth`  
   复盘与成长

7. `social_learning_collaboration`  
   协作与社会性学习

每个维度输出：

- level
- reason
- evidence
- evidence_status
- missing_information

## 11.3 总体输出

Auto 模式还提供：

- attention_level
- summary
- warnings

attention_level 用于帮助 HR 快速判断“是否值得进一步阅读”，不是人格测评，也不是对候选人未来潜力的确定性预测。

# 12. HR 指定人材分析（Specified）

## 12.1 使用目的

不同岗位和组织对“想要的人”定义不同。

因此 RA 允许 HR 自行输入 desired traits，例如：

- 主体性；
- 真面目；
- 学习速度快；
- 善于跨部门协调；
- 能在模糊环境中推动工作。

系统随后根据候选人简历中的事实，判断每一项特征的支持程度。

## 12.2 输出内容

每个指定 trait 输出：

- trait
- fit_level
- reason
- evidence
- evidence_validation_issues
- missing_information

整体输出：

- specified_fit_level
- summary
- warnings

若没有足够证据，应明确表达证据不足，而不是为了满足 HR 预设而强行匹配。

候选人列表承担“快速比较与缩小范围”的职责。

主要展示：

- 候选人；
- Job Match Score；
- must-have 状态；
- 匹配摘要；
- Auto 潜力信号摘要；
- Specified 人材特征摘要；
- 分析状态；
- 操作入口。

支持：

- 按岗位匹配分升序 / 降序排序；
- 多选候选人；
- 全选；
- 批量再评价；
- 查看原始简历；
- 进入详情；
- 从当前岗位移除候选人。

# 14. 批量再评价

HR 可以选择多个候选人，并选择需要重新运行的分析类型：

- 岗位匹配；
- Auto 潜力信号；
- Specified 人材分析。

Specified 模式要求先输入至少一个 desired trait。

批量再评价使用并行 Promise 调用，并以 `Promise.allSettled()` 汇总成功和失败结果，使部分失败不会抹掉已经成功的分析。

# 15. 候选人详情

候选人详情用于人工复核。

主要包括：

- 基本信息；
- 候选人结构化经历；
- Job Match Score；
- requirement 逐项匹配结果；
- must-have 结果；
- reason；
- evidence；
- evidence verification 状态；
- missing information；
- warnings；
- Auto 潜力信号；
- HR 指定人材分析；
- 原始 PDF 查看入口。

产品原则：

> 详情页不是再生成一个“AI 最终结论”，而是把判断拆开，让 HR 能看到为什么、依据是什么、哪里还不能确定。

---

# 16. 候选人池与删除语义

RA 区分两种操作：

## 16.1 从当前岗位移除

删除 JobCandidate 关联。

结果：

- 当前岗位不再显示该候选人；
- Candidate 本身仍保留；
- 如果该 Candidate 还关联其他岗位，不受影响。

## 16.2 删除 Candidate

删除全局候选人实体及其相关关系 / 结果。

适用于明确不再需要保存该候选人的情况。

- `ja-JP`

## 17.2 分析语言

# 21. AI / LLM 设计原则

## 21.1 使用范围

LLM 主要用于：

- JD Parsing；
- Resume Parsing；
- Job Match；
- Talent Discovery；
- Translation。

## 21.2 结构化输出

模型输出必须经过 Pydantic Schema 校验。

若返回结果不符合预期结构，应作为模型响应错误处理，而不是静默编造字段。

## 21.3 Prompt Injection 防御

当前项目定位为原型 / MVP 验证。

防御重点放在：

- 将简历和 JD 明确作为“数据”传给模型；
- 在系统提示中限制模型服从简历正文中的指令；
- 通过结构 Schema、Evidence Verification 和业务规则控制模型输出。

当前版本没有对简历正文采用激进关键词过滤，以避免过滤器误伤真实履历内容。

## 21.4 Provider

RA 使用 OpenAI Python SDK 兼容接口，可通过环境变量连接 OpenAI-compatible LLM 服务。

不同模块可以独立切换 Mock，便于：

- 无 API 环境运行；
- 测试；
- 前后端开发；
- 演示失败隔离。

# 22. 异常处理

| 场景 | 系统行为 |
| --- | --- |
| JD 为空 / 太短 | 阻止解析并返回参数错误 |
| JD 模型调用失败 | 返回明确错误，不保存虚假结果 |
| 非 PDF 文件 | 上传阶段拒绝 |
| 单次超过 30 份 PDF | 上传阶段拒绝 |
| PDF 无文本 | 单项解析失败 |
| LLM 请求失败 | 对应操作失败并返回服务错误 |
| LLM JSON / Schema 不合法 | 返回模型格式错误 |
| 批量单项失败 | 其他任务继续 |
| Evidence 无法验证 | 标记 needs_review |
| Evidence 不存在 | 标记 insufficient_evidence |
| Candidate 不属于当前 Job | 岗位评分接口拒绝 |
| 指定人材分析无 desired traits | 拒绝执行 |
| 原始 PDF 丢失 | 查看原简历时返回明确错误 |

# 24. 最终 MVP 验收标准

以下条件构成当前 RA 的最终 MVP 完成标准：

1. 用户可以登录系统；

# 25. 与初期 PRD 相比的主要演进

最终产品没有机械照搬初期方案，而是在开发验证中进行了以下收敛与增强。

## 25.1 三个独立分数 → “岗位匹配 + 潜力信号 + HR 指定人材”

初期方案设计：

- 岗位匹配分；
- 证据潜力分；
- 开放发现分。

最终实现调整为：

- Job Match：保留 0-100 分；
- Auto Talent：使用固定七维潜力信号和 attention level；
- Specified Talent：使用 HR 自定义特征进行适配分析。

原因：

- “潜力”本身很难被可靠地压缩成一个精确数值；
- 分维度展示更利于解释；
- HR 自定义人材特征比单一开放发现分更贴近实际招聘使用。

## 25.2 结果展示 → Evidence Verification

初期方案要求“给理由和证据”。

最终实现进一步区分：

- 有证据且验证通过；
- 有证据但需要复核；
- 没有足够证据。

这使“AI 解释”从单纯生成文字，升级为可供 HR 复核的证据语义。

## 25.3 简单批量循环 → 异步任务化

初期仅要求一次上传 10-30 份并逐份处理。

最终增加：

- 后台任务；
- 单项状态；
- Semaphore 并发控制；
- 失败隔离；
- 单项重试；
- 上传后离开页面仍可继续处理的任务语义。

## 25.4 单岗位候选人 → 全局 Candidate Pool

最终将 Candidate 与 JobCandidate 分离，使一个候选人可以跨岗位复用。

## 25.5 后续项转为实际功能

初期文档中列为后续增强的一部分功能已经实际实现，包括：

- 本地数据库；
- 原始简历查看；
- JD 人工调整；
- 候选人持久化；
- 异步处理；
- 多语言；
- 候选人管理。

## 25.6 增加精确简历去重

最终增加 SHA-256 精确文件去重，在不引入误合并风险的前提下减少重复解析和 LLM 调用。

## 25.7 增加日本招聘材料适配

最终增加“候选人文件夹上传”：

- 一名候选人可包含履歴書 + 職務経歴書等多份 PDF；
- 前端合并后仍沿用统一后端处理链。

# 28. 最终产品定义

RA 的最终定位可以概括为：

> **不是替 HR 决定“要不要这个人”，而是帮助 HR 在大量简历中更快知道“先看谁、为什么值得看、依据在哪里、哪里还需要确认”。**

产品价值由三部分组成：

- **效率**：减少重复阅读和机械整理；
- **区分度**：通过岗位匹配、潜力信号和人材像让候选人更容易比较；
- **可信度**：通过理由、证据、证据校验和缺失信息提示，让 AI 结果可被人工检查。

这也是当前最终实现相较于初期“简历打分工具”最大的产品演进。
